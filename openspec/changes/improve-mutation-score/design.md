## Context

See `proposal.md` for motivation. Current state relevant to this design:

- Mutation score **70%** (1714 killed + 4 timeout = 1718 detected / 2445 mutants). Reaching 85% requires **~361** more kills (2445 × 0.85 = 2078 → 2079 detected).
- Survivors (727) split by mutator class: **243** relational (`lt`/`gt`/`ge`/`le`), **196** equality (`eq_to_ne`/`ne_to_eq`), **167** arithmetic (`add`/`sub`/`mul`/`div`/`rem`), **121** inc/dec (`post`/`pre`).
- Survivors are heavily concentrated: the top 10 modules hold 372 (51%), the top 20 hold 491 (67%), and a long tail of 84 files with ≤5 mutants holds 177 (24%). `compiler.cpp` (106) and `resource_akm_reader.cpp` (75) alone are ~25% of the survivors.
- Round 1 of this change (66% → 70%) sampled one representative case per branch and left the rest unreached — its peephole test, its both-sides equality tests, and its relocation test each exercised a subset of the branches they targeted, which is why `compiler_code_optimizer.cpp` still has 23 survivors, `compiler_expression_evaluator.cpp` 42, and `compiler.cpp` 106.
- Tests are doctest 2.4.11 in `tests/unit/src/*.cpp`, one `test_unit` binary. `make mutation-run` uses `mull-runner-18 --timeout 32000 --minimum-timeout 32000 --allow-surviving --test-suite-exclude=Slow`.
- mull-runner 0.34.0 exposes **no per-mutant filter** (only `--dry-run` to enumerate without executing), so incremental verification is `make -C tests/unit run`; the full `make mutation-run` is a user-managed step. New tests compile without `-fpass-plugin`, so they do not change the mutant count.

## Goals / Non-Goals

**Goals:**
- Kill ≥ 361 survivors with test-only changes, ordered easiest → hardest, driven by the exact survivor locations in `mutation_report.json`.
- Exhaust the reachable branches of each targeted module rather than sample them.
- Reach 85% via kills; use `excludePaths` narrowing only as a fallback for provably equivalent mutants.

**Non-Goals:**
- Do NOT change production source code (`.cpp`/`.h` under `src/`).
- Do NOT convert the 4 timeout mutants to killed; they stay "Timeout".
- Do NOT run the full mull suite or `mutation-clean` during development (both are slow); verification is `make -C tests/unit run`, and the full `make mutation-run`/`make mutation-check` is the user's final step.
- Do NOT add `--dry-run`-based mutant enumeration as a workflow; it is unnecessary since the report already gives exact locations.

**In scope (fallback only):** `mull.yml` (`excludePaths`) — build/mutation config, not production code.

## Decisions

### Decision 1: Mutant-report-driven targeting

Each phase is scoped to the exact surviving mutant locations (file + mutator + line) from `mutation_report.json`. A phase's target list is generated by filtering the report, so every new test maps to concrete survivors.

- Rationale: Round 1's generic "add more subtype tests" did not move the needle; the survivors live in specific branches (opcode equality, immediate values, boundary comparisons) that generic tests never hit.
- Alternative: repeat the prior tier recipe — rejected; it already under-delivered.

### Decision 2: Exhaustive enumeration over representative sampling

Round 1 sampled one representative case per branch and left the rest unreached. Round 2 enumerates **every reachable case** for each targeted branch:

- the relocation switch in `compiler.cpp` → every reachable conditional `call`/`jp` opcode and the `0xFF` LOAD case (not just `jp z`/`jp nz`/`jp`);
- the AKM/AKX/MTF/SPR readers → every size boundary (`==`, `±1`) and every malformed/truncated error path, not just one boundary fixture;
- `compiler_expression_evaluator` and the graphics strategies → every `==`/`!=` type/subtype pair, not a couple of representative pairs;
- `compiler_code_optimizer` → every peephole pattern and every immediate-value branch, not the subset added in Round 1.

- Rationale: this is the core lesson of Round 1 — partial branch coverage leaves the majority of a module's mutants alive.
- Trade-off: more test code and fixtures, but each is data-driven and cheap once the enumeration is written.

### Decision 3: Phase ordering and kill budget

```
Phase 1 — easy   counters & boundary arithmetic   ~110-170 kills   (inc/dec + relational on tested paths)
Phase 2 — medium binary readers & strategies       ~130-190 kills   (boundary/malformed fixtures + both-sides)
Phase 3 — hard   type dispatch & relocation        ~75-120  kills   (eq_to_ne dispatch + relocation arithmetic)
Phase 4 — fallback scope narrowing                 0 kills          (only if equivalent mutants block 85%)
```

Ordering rationale: inc/dec and boundary mutants on already-tested paths need only an added assertion (lowest effort per kill); the binary readers need fixtures but are data-driven (medium); the `eq_to_ne` type dispatch and relocation arithmetic are the most expensive and carry the most equivalent-mutant risk (highest effort, done last). Phase 4 is a safety valve, not a planned phase.

### Decision 4: White-box relocation tests cover every reachable opcode

The relocation switch (`Compiler::write`, `compiler.cpp` lines ~508-675) is exercised directly, not via BASIC that must coincidentally emit a given byte sequence. The existing MegaROM fixup test (Round 1 task 5.1) is extended to seed the fix list with a crafted fix for **every reachable opcode case** — conditional `call` (`nc`/`nz`/`c`/`z`), conditional `jp` (`nc`/`nz`/`c`/`z`), unconditional `call`/`jp`, and the `0xFF` LOAD case — and assert the exact emitted bytes, killing the `add`/`sub`/`mul`/`div`/`rem` and boundary mutants in each case body.

- The `jp m`/`pe`/`p`/`po` and `call p`/`po`/`m`/`pe` variants are **never emitted** by the compiler (no flag-tracking at that granularity); they remain unreachable and are candidates for Phase-4 scope narrowing, not white-box tests.
- Rationale: generating BASIC that emits each conditional across a 16 KB segment boundary is impractical; `Compiler::write` already exposes the fixup logic.
- Alternative: byte-exact fixtures through full compilation — rejected as too brittle and slow.

### Decision 5: Readers get exhaustive boundary + malformed fixtures

For `resource_akm_reader.cpp` (75 survivors), `resource_akx_reader.cpp`, `resource_mtf_map_reader.cpp`, `resource_spr_reader.cpp`, and `resource_csv_reader.cpp`, add fixtures at every size boundary (`==`, `±1`) and truncated/malformed inputs that drive each error path and both sides of every size comparison. These are data-driven and cheap once the boundary matrix is written.

### Decision 6: Type-dispatch equality is driven per pair

The `eq_to_ne` survivors in `compiler_expression_evaluator.cpp` (30), `compiler_copy/line/put/circle/get_statement_strategy.cpp`, `compiler_symbol_resolver.cpp`, and `compiler_variable_emitter.cpp` are killed by driving every type/subtype pair through the dispatch and asserting the emitted result. Where a subtype is unreachable by construction, it is recorded and left for Phase-4 consideration rather than faked.

### Decision 7: Verification is unit-suite only; single-mutant runs are unavailable

mull-runner 0.34.0 has no `--mutant`/`--include` filter, so a single-mutant run is not possible. Every task therefore verifies with `make -C tests/unit run` (fast, incremental; new tests compile without the mull frontend). No `mutation-build`, no `mutation-run`, and no `mutation-clean` are performed by the implementer. The user runs `make mutation-run` + `make mutation-check` once at the end to confirm ≥ 85%.

### Decision 8: Narrow the mutation scope only as a fallback

If Phase 3 leaves provably equivalent or unreachable mutants that block 85%, extend `mull.yml` `excludePaths` to exclude the specific defensive/unreachable regions (for example, the never-emitted relocation opcode cases, or defensive guards whose both branches are observably identical). This reduces the denominator rather than killing, so it is applied only after the test-led phases, and only for code whose equivalence is demonstrated in the design/tasks notes.

- Rationale: `excludePaths` is legitimate for third-party/unreachable code (already used for `pletter.cpp`), but over-applying it defeats the point of a mutation bar. It stays a last resort.
- Alternative: keep everything mutated and fail the 85% bar on equivalent mutants — rejected; equivalent mutants are, by definition, not killable.

**Outcome after implementation (task 10.1):** no additional `excludePaths` entries were added. Investigation showed `excludePaths` matches **whole file paths** (regex), so it cannot target individual switch cases, functions, or the never-emitted opcode branches. The unreachable/equivalent mutants identified during Phases 1–3 are scattered across files that also contain reachable code:

- `compiler.cpp` — never-emitted `jp m/pe/p/po`/`call p/po/m/pe` relocation cases, plus the reachable build/segment logic;
- `compiler_code_optimizer.cpp` — the `*pipeline[0] == 11` (should be `0x11`) dead peephole branch;
- `resource_akm_reader.cpp` — the linker state machine (out of scope by decision).

Excluding any of these whole files would also drop a large number of reachable, killable mutants and distort the score. The user therefore accepted these unreachable mutants in the final count, and `mull.yml` remains unchanged (only `pletter.cpp` excluded, as in Round 1).

### Decision 9: Carry forward Round 1's runtime/scope decisions

Decisions already made and implemented in Round 1 remain in force and are not re-decided here:

- Slow-test exclusion: the 8 KB blob test is tagged `TEST_SUITE("Slow")` and skipped during mutation via `--test-suite-exclude=Slow`, but still runs in `make run`.
- Timeout: `--timeout 32000 --minimum-timeout 32000` (the measured baseline ~27 s mull / ~45 s gcc exceeds the old 10-15 s assumption; no further change needed).
- doctest/test code is already out of mutation scope (test objects compile without `-fpass-plugin`).
- `--ld-search-path /lib/x86_64-linux-gnu:/lib64` silences the JIT library warnings.
- `pletter.cpp` is already excluded via `excludePaths`.

## Risks / Trade-offs

- [Risk: 85% may still be unreachable purely by tests on equality-heavy and relocation arithmetic code] → Mitigation: Phase 3 order puts the two largest gaps first; Phase 4 narrows the denominator via `excludePaths` for provably equivalent/unreachable regions.
- [Risk: exhaustive fixtures bloat the suite and raise the mull baseline] → Mitigation: keep fixtures minimal and data-driven; the `Slow`-suite exclusion already offsets the single largest test.
- [Risk: white-box tests couple to internal pipeline layout] → Mitigation: assert observable byte/value output, not internal indices.
- [Trade-off: accepting 4 timeout mutants] → They cost < 0.2% of score and are a healthy signal that loops are exercised; not worth eliminating.

## Migration Plan

1. Phase 1 + Phase 2 + Phase 3: add tests, verifying each batch with `make -C tests/unit run`.
2. After each phase, re-check the surviving list in `mutation_report.json` mentally against the new tests (no full mull run).
3. If Phase 3 shows provably equivalent/unreachable mutants remain, apply the Phase-4 `mull.yml` `excludePaths` fallback and document it.
4. Run the full unit suite and confirm all prior tests pass and the count increased.
5. User runs `make mutation-run` + `make mutation-check` once at the end to confirm ≥ 85%.
