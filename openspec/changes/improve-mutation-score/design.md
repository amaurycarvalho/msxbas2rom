## Context

See `proposal.md` for motivation. Current state relevant to this design:

- Mutation score **66%** (1695 killed + 9 timeout = 1704 detected / 2549 mutants). Reaching 85% requires killing **463** more survivors (2549 × 0.85 ≈ 2167 detected).
- Survivors (845) split by complexity: **330** arithmetic/inc-dec, **284** relational/boundary, **231** equality (`eq_to_ne`/`ne_to_eq`).
- Tests are doctest 2.4.11 in `tests/unit/src/*.cpp`, one `test_unit` binary. `make mutation-run` uses `mull-runner-18 --timeout 32000 --minimum-timeout 32000`.
- Measured full-suite wall time (gcc `--coverage` build) is **45.69 s**; the slowest single test is 12.7 s (`ResourceBlobPackedReader packs data at the 8K boundary`).
- The prior attempt added subtype/omitted-argument tests and moved the score only 65% → 66%; the code optimizer, the relocation conditional-opcode switch, and the complex binary readers were effectively untouched.

## Goals / Non-Goals

**Goals:**
- Kill ≥ 463 survivors with test-only changes, ordered by kills-per-effort.
- Drive test placement from `mutation_report.json` locations (mutator + line), not from generic "add more subtype tests".
- Reduce the mull baseline by excluding the slowest tests from mutation runs (via a `Slow` suite), while keeping them in the normal unit-test suite.

**Non-Goals:**
- Do NOT change production source code (`.cpp`/`.h` under `src/`).
- Do NOT convert the 9 timeout mutants to killed; they stay "Timeout".
- Do NOT pre-apply a `Makefile` timeout change; only adjust it if the baseline-verification task proves it necessary.

**In scope (Phase B):** `mull.yml` (`excludePaths`) and the `Makefile` `mutation-run` target (`--ld-search-path`) — these are build/mutation config, not production code.

## Decisions

### Decision 1: Mutant-report-driven targeting

Rather than the prior tier recipe (which over-promised kills), each phase is scoped to the exact surviving mutant locations from `mutation_report.json`. A phase's target list is generated by filtering the report by file and mutator class, so every new test maps to concrete survivors.

- Rationale: the prior plan's generic "subtype" and "omitted-argument" tests did not move the needle because the real survivors live in specific branches (opcode equality, immediate values, boundary comparisons) that generic tests never hit.
- Alternative: repeat the prior tier approach with more cases — rejected; it already under-delivered.

### Decision 2: Phase ordering and kill budget

```
Phase A — resource readers + pletter + rom.cpp      ~200 kills (arith/boundary)
Phase B — mull scope + runtime optimization          narrows denominator, speeds up runs
Phase C — semantic helpers + code optimizer          ~120 kills (equality)
```

A checkpoints after each phase via a user-run `make mutation-run` (mull is never run by the agent). Phase C is last because equality mutants are the most expensive to kill, but it includes the two highest-value gaps (code optimizer ~56, expression evaluator ~38). Phase B shifts strategy from "kill graphics survivors" (which proved to be dominated by equivalent and byte-exact-required mutants) to "reduce the mutant denominator and the per-run baseline".

### Decision 3: White-box tests for the code optimizer and relocation switch

Both hard targets are exercised directly rather than via BASIC that must coincidentally emit the right byte sequence.

- **Code optimizer** (`CompilerCodeOptimizer::addByteOptimized(byte)`): a new `test_code_optimizer.cpp` primes a `CompilerContext` code pipeline with the exact byte sequences each peephole pattern matches (e.g. `0x21 … 0xE5 0x21 …` for the `pop de` pattern, and `add hl,de` with immediates 1/2/3), then calls `addByteOptimized` and asserts the resulting pipeline bytes.
- **Relocation switch** (`Compiler::write(dest, start_address)`, `compiler.cpp` lines 546–689): extend the existing MegaROM fixup tests (`test_compiler.cpp`) to seed the fix list with a crafted fix whose target byte is each conditional opcode (`0xF4/0xE4/0xFC/0xEC`, `0xD4/0xC4/0xDC/0xCC`, `0xFA/0xEA/0xF2/0xE2`, `0xD2/0xC2/0xDA/0xCA`, and `0xFF`), then assert the emitted bytes. This follows the pattern already used for the `0xC3`/`0xCD` paths.

- Rationale: generating BASIC that emits each conditional call/jp across a 16 KB segment boundary is impractical; the fixup logic is already exposed via `Compiler::write`.
- Alternative: byte-exact fixtures through full compilation — rejected as too brittle and slow.

### Decision 4: Complex readers get boundary + malformed fixtures

For `resource_akm_reader.cpp` (87 survivors), `resource_akx_reader.cpp`, `resource_mtf_map_reader.cpp`, and `resource_spr_reader.cpp`, add fixtures at exact size boundaries and truncated/malformed inputs that drive the error paths and both sides of size comparisons. These are data-driven and cheap once fixtures are written.

### Decision 5: Exclude slow tests from mutation via a doctest suite filter

Mull runs the full suite once per mutant, so total wall time ≈ `baseline × mutants / workers`. With `nproc = 4` (`--workers` is already maxed) and a baseline of ~27 s, 2549 mutants take ~4.8 h — the baseline is the only meaningful speed lever.

- `ResourceBlobPackedReader packs data at the 8K boundary` (~12.7 s, ≈45% of the baseline) is tagged with a dedicated `TEST_SUITE("Slow")` (assertions unchanged), and the `mutation-run` target passes `--test-suite-exclude=Slow` as a Mull runner arg. The test still runs in the normal `make run`; only the Mull warm-up/baseline/mutant runs skip it.
- Rationale: shrinking the fixture would lose the 8 KB acceptance boundary; a faster data pattern would change the test. Excluding it from the mutation run keeps the test intact while cutting the baseline roughly in half (and, via `baseline*10`, shrinking the per-mutant hang timeout).
- Trade-off: the exact-8 KB accept path of `ResourceBlobPackedReader::pack()` is no longer exercised during mutation, so its `> 0x2000` boundary mutant may survive. The fast `rejects data over the 8K boundary` test (0x2001) still covers the reject side, and the small-data tests cover the pack path — only the exact-boundary side is lost. Accepted in exchange for ~2× faster Mull runs.
- Alternative: `--test-case-exclude=*packs data at the 8K boundary*` by name (zero test change) — rejected: name-based filters are brittle and don't scale to other slow tests; the `Slow` suite is explicit and extensible (other slow tests such as the meta-tests can be added later).

**Full top-10 slow-test evaluation.** The remaining nine slow tests were measured and evaluated for the same exclusion, and are **kept in the mutation suite** (not tagged `Slow`):

| Test | Time | Gain (~min) | Verdict |
|---|---|---|---|
| `All statement strategies execute successfully` | 1.93 s | ~20 | **Keep** — primary line coverage for ~70 statement strategies + factory dispatch; excluding drops minor strategies' mutants from the report. |
| `All function strategies execute successfully` | 1.76 s | ~19 | **Keep** — same, for function strategies. |
| `Function strategies handle decimal/string argument subtypes` | 1.67 s | ~18 | **Keep** — targeted subtype-branch coverage added by the prior change; excluding undoes those kills. |
| `All CMD instruction handlers execute successfully` | 1.03 s | ~11 | **Keep** — primary coverage for CMD handlers. |
| `PRINT statement` | 0.95 s | ~10 | **Keep** — end-to-end real `.bas` compile (lexer+parser+compiler). |
| `Resolves cross-segment conditional jumps in MegaROM` | 0.79 s | ~8 | **Keep** — unique coverage for the reachable relocation opcodes (task 5.1). |
| `Math functions compile with numeric/single/double arguments` | 0.68 s | ~7 | **Keep** — targeted subtype-branch coverage. |
| `Builds multi-page ROM in MegaROM mode` | 0.50 s | ~5 | **Keep** — ROM multi-page layout coverage. |
| `SET sub-commands compile successfully` | 0.44 s | ~5 | **Keep** — SET sub-command coverage. |

Together these nine total ~10 s (~28% of the baseline) and would save ~1.7 h, but they cover core compiler logic — strategy dispatch, subtype branches, and relocation — whose loss outweighs the speed gain. Only the 8 KB blob test is excluded, because its coverage is third-party `pletter.cpp` (already excluded by Decision 7) plus a pack boundary already covered by the small-data tests. If a larger speedup is ever needed, the three meta-tests (`All … strategies/handlers`) are the next candidates, at the cost of dropping shallow success-path coverage for the minor strategies.

### Decision 6: Verify the timeout baseline before touching it

The spec currently assumes a 10–15 s baseline but the suite measures ~45 s (gcc build) / ~27 s (mull warm-up). Add a verification task to time the actual mutation test binary (`bin/Mutation/test_unit`). Only if the baseline exceeds the current 32 s `--timeout` is the flag adjusted (this is a wall-clock correction, not a score change).

### Decision 7: Narrow the mutation scope to project-owned code

Add `excludePaths` to `mull.yml` for `src/infrastructure/compression/pletter.cpp` (adapted third-party from XL2S). This narrows the mutant denominator to project-owned logic, making the 85% target more meaningful and reducing wall-clock (fewer mutants to run). Do NOT use `gitDiffRef` — CI diff-based scoping is not the objective.

- Rationale: pletter is adapted third-party code whose 28 survivors include loop-hang timeouts and O(n²) packing arithmetic with low signal. The embedded kernel assembly (`src/infrastructure/kernel/asm/*.asm`) needs no `excludePaths` entry — it is already outside the mutation scope because only `.cpp` files are compiled with the Mull frontend; the sole `.cpp` in that directory (`z80.cpp`) is project-owned opcode-emitter code with no mutation points.
- Alternative: keep everything mutated and keep trying to test third-party code — rejected: low value, high wall-clock cost.

### Decision 8: doctest is already out of scope; silence the JIT library warnings

- Test objects are compiled **without** `-fpass-plugin=$(MUTATION_FRONTEND)` (Makefile `$(MUTATION_OBJDIR)/test/%.o` rule), so doctest and all test code already carry no mutation points — no action needed beyond recording this.
- The `Could not find dynamic library: libm.so.6/libc.so.6/ld-linux-x86-64.so.2` warnings are cosmetic (the libs exist under `/lib/x86_64-linux-gnu`); add `--ld-search-path /lib/x86_64-linux-gnu:/lib64` to `mutation-run` to silence them. No performance effect.

## Risks / Trade-offs

- [Risk: 85% may still be unreachable purely by tests on the equality-heavy semantic files] → Mitigation: Phase C order puts the two largest gaps first; Phase B narrows the denominator via `excludePaths`, which independently raises the score; if a specific branch proves untestable white-box, surface it before further narrowing scope.
- [Risk: white-box tests couple to internal pipeline layout and break on refactor] → Mitigation: assert observable byte output, not internal indices, wherever possible.
- [Risk: new tests increase suite wall time, raising the mull baseline] → Mitigation: keep fixtures minimal; re-run the duration measurement after each phase; Phase B 3.4 targets the 8 KB blob test directly.
- [Risk: exact-boundary fixtures are brittle] → Mitigation: assert observable outcomes (error messages, code size, output bytes) rather than raw internals.
- [Trade-off: accepting 9 timeout mutants] → They cost ~0.35% of score and are a healthy signal that loops are exercised; not worth eliminating. Note: 5 of the 9 are in `pletter.cpp`, which Phase B excludes — the remaining timeouts will not re-appear.

## Migration Plan

1. Phase A + Phase C: add tests, verifying each with `make -C tests/unit run` after every batch.
2. Phase B: apply `mull.yml` `excludePaths` and the `Makefile` `--ld-search-path` flag, then tag the 8 KB blob test `Slow` and pass `--test-suite-exclude=Slow`; verify with `make run` and `bin/Mutation/test_unit --test-suite-exclude=Slow`.
3. After all phases, run the full suite and confirm all prior tests pass and the count increased.
4. User runs `make mutation-run` + `make mutation-check` once at the end to confirm ≥ 85%.
5. If the baseline-verification task shows the suite exceeds the timeout, adjust `Makefile` `mutation-run` flags and re-verify.
